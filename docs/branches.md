# Ветки GitHub-репозитория

## Принятая схема

Одна постоянная ветка `main` содержит принятую общую версию документации и кода. От неё создаётся отдельная короткоживущая ветка для каждой задачи. После Pull Request, review и merge такая ветка удаляется. Это соответствует лёгкому GitHub Flow.

| Имя | Назначение | Когда создать |
| --- | --- | --- |
| `main` | Общая принятая версия, контрольные точки | При создании репозитория |
| `docs/checkpoint-1` | Этот комплект документов и прототип | При загрузке комплекта |
| `feat/frontend-chat` | Реализация чата на React | Когда frontend начинает задачу |
| `feat/backend-api` | Каркас Go API и сессии | Когда backend начинает задачу |
| `feat/rag-bm25` | Подготовка индекса и поискового API | Когда RAG начинает задачу |
| `infra/compose` | Контейнеры и локальный запуск | При соответствующей задаче |
| `fix/<problem>` | Исправление | Когда обнаружена ошибка |

Имена — примеры, не требование создать все ветки заранее. В каждый момент нужны `main` и ветки реально выполняемых задач. После первого checkpoint новый этап начинается новыми ветками от актуальной `main`.

`frontend`, `backend`, `rag` — каталоги и роли; они не обязаны быть постоянными ветками. `develop`, `release`, `hotfix` как постоянные ветки для этой команды не вводятся. При необходимости конкретного релиза достаточно тега.

## Создание ветки участником

```bash
git switch main
git pull --ff-only
git switch -c feat/rag-bm25
```

Менять имя соответственно задаче. Не начинать новую задачу от старой несмерженной feature-ветки без осознанной зависимости.

## Настройки `main`

Если доступны branch protection/rulesets: требовать Pull Request, минимум один review другого участника, разрешение обсуждений и существующий успешный check `docs-check`. Запретить force-push и удаление `main`; не обходить правила обычной административной правкой. Для удобства можно включить squash merge и автоматическое удаление feature-веток.

Добавлять обязательный status check только после того, как workflow реально появился и выполнился. Не требовать несуществующие Go/React/GPU-проверки на первом этапе.

Техническая защита зависит от тарифа и видимости: GitHub Free предоставляет её в публичных репозиториях; для private-репозитория используются соответствующие платные тарифы. Если настройка недоступна, оставить private-репозиторий и соблюдать PR/review вручную либо выбрать подходящий доступный тариф; само это руководство не включает защиту автоматически.

## Фиксация первой точки

После merge всех материалов и успешной демонстрации на актуальной `main`:

```bash
git switch main
git pull --ff-only
git tag -a checkpoint-1 -m "Checkpoint 1: specification and interface prototype"
git push origin checkpoint-1
```

`checkpoint-1` — **тег**, а не ещё одна ветка. Не ставить тег до проверки; при уже существующем теге не перезаписывать его, а выбрать новый явно обозначенный тег исправленной версии.
