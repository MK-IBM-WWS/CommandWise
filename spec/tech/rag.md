# Спецификация BM25 и RAG

Search строит инвертированный индекс и ранжирует фрагменты. Go формирует запрос к Qwen3-14B Q4_K_M в llama.cpp и возвращает ответ с источниками.

## Корпус и предварительная обработка

Смысловые Markdown-разделы становятся отдельными индексируемыми фрагментами. Они сохраняют заголовки, условия применения, примеры и ссылку на первоисточник. Разбиение по заголовкам сохраняет целыми многострочные команды и блоки кода. `chunk_id` зависит от текста и метаданных. Manifest перечисляет Debian, Fedora и Arch. Общие разделы индексируются для всех трёх. Раздел конкретной системы помечается в applies_to одним дистрибутивом.

При первом запуске и при смене ревизии Search включает во встроенный корпус только Markdown-файлы, перечисленные в `corpus/manifest.json`. Имена лишних Markdown-файлов попадают в журнал. Если файла из манифеста нет, публикация останавливается с указанием его имени. При обновлении к встроенному корпусу добавляются ранее опубликованные документы администратора.

Тот же токенизатор используется для корпуса и вопроса. Регулярное выражение выделяет русские и латинские слова, имена команд, флаги, пути и числа с суффиксами. Технические токены важны для вопросов по CLI: `-r` и `-R` сохраняют регистр, путь и размер остаются единицами поиска. Приведение русских слов к нижнему регистру, нормализация «ё» и стемминг Snowball уменьшают влияние падежей и числа на совпадение. Стемминг выбран как лёгкая нормализация короткого корпуса, которой достаточно для многих словоформ без словарного морфологического разбора. Ошибочные совпадения после стемминга оцениваются на benchmark. Перечень частых служебных слов применяется к запросу, поскольку такие слова слабо отличают разделы. Несколько прозрачных групп синонимов связывают частые русские формулировки. Модель и интерфейс получают исходный текст.

## Инвертированный индекс и формула BM25

`search/bm25_index.py` строит словарь `терм → [(порядковый ID фрагмента, TF)]`. Длины документов хранятся отдельно. Для слова DF равно длине его списка. (N) — количество фрагментов, (avgdl) — средняя длина в токенах. Нормировки и IDF вычисляются при загрузке, запрос идёт по спискам совпавших терминов.

```text
IDF(t) = ln(1 + (N − DF(t) + 0,5) / (DF(t) + 0,5))
BM25(q,d) = Σ IDF(t) · TF(t,d) · (k1+1) / (TF(t,d) + k1·(1−b+b·|d|/avgdl))
```

Параметры `k1=1.5` и `b=0.75` зафиксированы в индексе. Индексатор сохраняет `bm25.json` и его контрольную сумму. При чтении старого снимка с `tokens.json` инвертированный индекс восстанавливается тем же собственным кодом. Обновления корпуса публикуются атомарно. Для неизменившихся фрагментов переиспользуются векторы E5.

Поиск применяет веса заголовков и расширение запроса. Применимость к дистрибутиву проверяется до выбора top-k. Для общего запроса об обновлении пакетов поднимается штатный менеджер выбранной системы. При явном запросе чужой пакетной команды возвращается раздел с подходящим аналогом. Если вопрос явно называет команду из корпуса, кандидаты ограничиваются этой командой или несколькими явно названными. До 20 кандидатов могут уточняться многоязычным E5 ONNX на CPU. Используются cosine similarity и взвешенное объединение обратных рангов с весами 2 для BM25 и 1 для E5. Для E5 применяются префиксы `query: ` и `passage: `, усреднение по маске и L2-нормировка.

## Генерация и оценка

Общий системный шаблон `backend/rag_system.txt` используется в приложении и benchmark. В запрос к Qwen попадают система, вопрос и нумерованные фрагменты. Для диалога сервер включает ограниченную историю и проверяет длину prompt. На запрос без совместимого кандидата возвращается `no_context`. Когда результаты лексически близки, но содержат мало сведений, отказ зависит от ответа LLM. Такие случаи включены в набор ловушек.

Два варианта retrieval оцениваются на одном зафиксированном корпусе. Затем Qwen отвечает по hybrid-выдаче. Четыре итоговые метрики, исходные данные, ответы и способ повторного запуска описаны в [benchmark](../../benchmark/README.md).
