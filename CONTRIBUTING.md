# Совместная работа

## Порядок SDD

Перед кодом описать поведение и способ проверки в соответствующей спецификации. Изменение API сопровождается обновлением контрактов, mock-примеров и потребителей. Исправление к уже принятой спецификации не требует переписывать всю документацию.

Небольшая задача → ветка → изменение спецификации → код → проверки → Pull Request → review коллегой → merge в `main`. Внешние сервисы, зависимости или несовместимые изменения добавляются по конкретной необходимости с записью причины.



## Ветки

Постоянная ветка — `main`. Для задач создаются временные ветки. Ветки «по участнику навсегда» и обязательная `develop` не вводятся.



## Команды одной задачи

Из чистого клона, после замены `OWNER/linux-rag` настоящим репозиторием:

```bash
git clone git@github.com:OWNER/linux-rag.git
cd linux-rag
git switch main
git pull --ff-only
git switch -c feat/backend-api
```

После изменения проверить `git status`, `git diff`, `git diff --check` и подходящие проверки. Добавлять конкретные файлы; пример для документации:

```bash
git add README.md spec/tech/architecture.md
git commit -m "docs: describe backend integration"
git push -u origin HEAD
```

На GitHub открыть Pull Request с base=`main`, описать поведение и фактические проверки, запросить review другого участника. После merge удалить временную ветку в GitHub и локально обновить `main`.



## Review

Проверяющий оценивает соответствие задаче, спецификацию, API, отсутствие секретов и результат проверки. Автор исправляет замечания. Самостоятельное подтверждение собственного PR не заменяет review коллеги. Если техническая защита веток недоступна в тарифе, команда всё равно соблюдает процесс PR; это организационное правило, а не активированное ограничение сервера.

Не удалять чужие изменения, не применять force-push к общей ветке, не переписывать публичную историю без специальной задачи. Оставлять изменение в одном PR достаточно небольшим для проверки.



## Готовность изменения

Спецификация и код согласованы; интерфейсы потребителей не сломаны; соответствующие проверки выполнены; README/CHANGE\_HISTORY обновлены при необходимости. В отчёте указаны пропуски и ограничения. Показатели benchmark и результаты тестов не выдумываются.
